# 三、宏

对于同一类别、命名规律一致、用途相近的一组宏（例如 EV_*、ABS_MT_*），默认不要把每个宏分别拆成独立小节详细整理。

1. 整组宏只使用一个标题。
2. 必需头文件只写一次。
3. 所有宏集中放在同一个 C 代码块中。
4. 每个宏在行尾使用简短注释说明作用。
5. 不需要为每个宏重复写作用说明、头文件和代码示例。
6. 只有当我明确要求详细整理某一个宏时，才单独展开。
7. 函数式宏、参数含义较复杂或需要配合其他函数使用的宏（例如 EVIOCGABS）仍然可以单独详细整理。

# 四、函数笔记格式

1. 函数笔记必须严格采用下面的结构。
2. 标题等级我会传入（例如：`整理笔记4` 表示使用四级标题 `####`）；如果我没有传入标题等级，则直接按照下面结构中的默认标题等级整理。
3. 不要给我要求整理的一个笔记设置与函数名同级的其他标题。函数名是该篇笔记唯一的同级标题，其他说明直接写正文，不要再增加“作用”“参数说明”“返回值”“注意事项”“示例”等同级小标题。
4. 函数所需的头文件必须和函数原型放在同一个 C 代码框中。
5. 函数注释必须使用 `@brief`、`@param`、`@retval` 的形式：
    - `@brief`：说明函数的主要作用。
    - `@param`：每个参数分别说明参数含义，必要时说明可取值及不同取值的作用。
    - `@retval`：分别列出不同返回值及其含义。
6. 如果某个函数本身没有特殊限制，但在操作某个具体芯片、设备或模块时存在额外要求，应在函数注释代码框中使用 `@note` 补充说明。
    这类额外要求包括但不限于：
    - 写入后需要等待一定时间；
    - 必须按照特定的访问顺序操作；
    - 某些状态下不能访问；
    - 参数受到具体硬件限制；
    - 芯片内部操作尚未完成时不能立即进行下一次操作；
    - 某个具体设备存在特殊的数据格式、时序或使用要求。
7. `@note` 必须明确区分“函数本身的规则”和“具体设备的规则”，不能让人误以为具体芯片的限制是该函数的通用要求。
    例如：

```c
/**
 * @note   当该函数用于 AT24C02 时，写入后芯片还需要进行 EEPROM 内部写操作，
 *         内部写周期 tWR 最大为 10 ms。
 *         简单处理时可延时 10 ms，也可以使用 ACK Polling 判断写入是否完成。
 *
 *         这里的 10 ms 是 AT24C02 芯片本身的要求，
 *         不是该函数本身要求的延时时间。
 */
```

8. 如果没有与具体设备、芯片或特殊使用场景相关的注意事项，则不要为了保持格式而强行添加 `@note`。
9. `@note` 中如果存在更规范、更推荐的处理方法，可以在说明简单做法的同时简要补充。例如“固定延时”之外还可以使用“ACK Polling”等方式。
10. 函数笔记默认结构如下：
#### 函数名

```c
/**
 * @brief  函数作用。
 *
 * @param  参数名: 参数含义。
 *
 * @retval 返回值情况1: 含义。
 *
 * @retval 返回值情况2: 含义。
 *
 * @note   与具体芯片、设备或特殊场景有关的注意事项。
 *         如果没有，则删除整个 @note 部分。
 */
#include <需要的头文件>

函数原型
```

代码框下面可以继续补充理解函数所必需的说明和简洁示例，但不要重复代码框中已经明确说明的内容，也不要添加与当前函数无关的扩展内容。

# 五、笔记分类与归档规则

整理笔记时，分类应遵守以下原则：

1. **按内容本质归类，不按出现位置归类。**  
   不要因为某个知识点第一次出现在某节课、某个源码文件或某类驱动中，就直接归到那里。应先判断它真正属于哪个技术层次、功能或机制。

2. **主要分类尽量少，内部再按需要细分。**  
   优先使用少量、清晰、长期稳定的主要分类，避免把每个小机制都拆成独立大类。  
   当某一类内容逐渐增多时，再在该分类下面继续细分。

3. **通用内容和专用内容分开。**  
   能被多个模块、子系统或场景共同使用的内容，放到更通用的分类；只属于某个具体模块、协议、设备、子系统或库的内容，再放到对应专用分类。

4. **同一个内容只整理一次。**  
   同一个宏、数据类型、结构体、函数或知识点，只在真正所属的位置整理一次，不因它在多个地方使用而重复整理。

5. **只在实际需要时新增分类。**  
   不提前建立大量空章节。现有分类能够合理容纳时，优先使用现有分类；只有确实无法合理归类时才新增。

6. **不同技术层次要分开。**  
   例如：

```text
Linux 命令
→ Linux 命令分类

编译器相关内容
→ 编译分类

Makefile 内容
→ Makefile 分类

用户空间接口
→ Linux 应用开发相关分类

内核接口
→ Linux 驱动开发相关分类

第三方库接口
→ 对应第三方库分类
```

7. **系统、第三方和自己编写的内容要区分。**  
   系统提供的内容放到对应系统分类；第三方库提供的内容放到对应库；自己编写的函数、宏、结构体默认不作为系统接口笔记整理，除非我明确要求。

8. **每个具体分类内部默认按内容类型整理：**

```text
宏
数据类型
函数
```

没有内容的类型不需要建立空小节。

9. **函数式宏按函数整理，但必须注明其本质是宏。**  
   普通常量宏、标志宏、修饰宏、属性宏等仍放在“宏”中。

10. **按当前实际使用的源码、头文件和版本判断真实定义。**  
    不要只根据名字或调用形式猜测它是宏、函数、函数式宏、数据类型还是结构体。

11. **源码只是寻找知识点的来源，不是分类依据。**  
    当我要求整理源码中的系统宏、数据类型和函数时，应分别判断每个知识点真正属于哪里，再决定放置位置。

分类的目标是：

```text
主要分类少而清晰
同类内容集中
查找方便
避免重复
需要时再细分
能够长期扩展
```
